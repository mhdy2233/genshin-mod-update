# PC：如何找差异、如何修改

适用于GIMI/3DMigoto角色MOD。先确认当前加载器的实际版本与配置格式；例子不能取代目标游戏的资源证据。

同版本修复也可使用本文的几何/材质方法；用户要主动改配色、部件、选项或几何时，先按 [定向修改](mod-editing.md) 明确目标。攻击/技能特效另读 [特效修改与修复](pc-effects.md)，不要把正常皮肤的骨骼或材质当作默认修复对象。

## 1. 基线与引用关系

保留用户原ZIP和解出的未修改目录，给文件做SHA256清单。区分原件、旧工具修过的副本、`.bak`和当前真正启用的目录；`DISABLED_`是否有效由实际加载器/include规则决定。不同角色可以共存，同一角色的互斥模型用独立候选测试。

不要用普通`configparser`读写GIMI INI：重复的`run`、条件块和语句顺序会被折叠或改变。将section和所有语句按原顺序保存，沿着TextureOverride→条件→资源/CommandList追踪。修改时定位**section、键、旧值及预期出现次数**；保留注释、编码、换行和未相关语句。运行第三方批量修复器前先读匹配条件、修改范围、映射方向和重复执行行为。

`inspect_mod.py`是只读盘点，不能求值INI条件。尤其是多个INI、include、namespace、引用别的MOD资源或动态变量，要手工核对当前实际分支。缺文件不等于新版本hash改变，先排除根目录或大小写解析问题。

## 2. 先排除数据自相矛盾

从**各Resource自己的声明**读取stride/格式，不能按文件名统一除以40。

| 检查 | 方法 | 修改原则 |
| --- | --- | --- |
| 每流顶点数量 | `文件字节数 % stride == 0`；Position、Blend、Texcoord各算数量，确认属于同一顶点域 | 不一致先找引用/导出问题；不裁剪尾部凑数 |
| draw | 非索引`draw=count,startVertex`与实际输入/输出范围核对 | 只有确定它负责该流生成时才按该流数量修改；不是把全部draw改成文件顶点数 |
| drawindexed | `count, firstIndex, baseVertex`按所选分支核对；范围不超IB，选中索引加baseVertex不超对应顶点流 | firstIndex单位是索引，不是字节；条件分段分别算 |
| IB格式 | R16=2字节、R32=4字节；检查整除、三角列表计数、最小/最大索引 | 在当前拓扑/加载器允许范围内保留有效格式；不能因参考MOD用R32就转换R16 |
| 浮点/权重 | 已确认布局后检查NaN/Inf、负权重、有权重索引范围 | 不顺手归一化原作者权重；保留零权重槽的填充值 |
| 顶点输出容量 | 核对目标对象的VertexLimitRaise标识/工具要求与替换顶点数 | 多于官方顶点是正常MOD情况；需要的是足够输出容量，不是无依据减面 |

错误可能叠加。只有hash和骨骼修正过、却缺扩容/正确draw的失败，不能单独判定remap错误。几何阶段一起改了三个前置条件，只能说明组合可用，不能说实验证明了某一个是唯一根因。

## 3. 找新hash与新绘制分段

按资源用途建立对照，不按文件里所有八位十六进制数字做全局替换：

`角色/皮肤 + 绘制部件 + VB/IB/CS/纹理用途 + stride/数量 + Shader/纹理关系 → 目标标识`

取证来源按可用性选择：

1. **目标客户端真实帧/资源**：确认当前加载器的hunting/frame analysis入口，定位目标角色、姿势、LOD和部件，保存帧dump中的draw call、VB/IB槽、stride/偏移、索引数、Shader及贴图。先知道哪个draw被匹配，再复制对应hash。按键以本机实际`d3dx.ini`或hunting说明为准，不能把一套热键推广到所有发行版。
2. **固定提交的角色资产表/生成器**：记录仓库URL、提交或发布版本、游戏适用范围和取证时间。`main`分支及网页搜索标题会漂移；需要当前值时读取实际发布内容。GIMI工具“6.0”和原神游戏“6.0”不是一回事。
3. **同目标版本已工作的同角色MOD**：用来交叉核对用途、分段和库调用。它的顶点数、IB格式和Blend不能直接搬给另一套衣服。

区分`hash`（匹配游戏对象/缓冲）、shader hash、资源PathID、文件SHA256：它们不是可互换的“新版本ID”。`match_first_index`匹配的是**游戏原绘制**，不是你替换后头发/身体的三角形数。新版本未改分段时保持旧分段，即使MOD更高模。

写出差异表后，只修改已经确认的用途行；同一个IB hash在IB/Head/Body多处出现时按用途覆盖完整。仍然有效的旧hash不为了“升级”而换。

## 4. 骨骼映射及受控修改

先回答：是否真的改变了骨骼索引，还是容量/绘制错误造成假扭曲？

- 优先比较同角色旧/新骨骼的唯一名称或hash、父子层级、bindpose及坐标约定，形成**旧索引→新索引**。
- 若引用社区修复表，读取实际对应角色的表，记录源代码/提交与输入适用范围，不凭“更新的修复器”标题采用。不同发布可能对该角色使用完全相同的映射。
- 跨多个骨骼变更断点时，分别确认每一步的输入/输出域，再组合成原包到最终目标的映射，例如`old_to_final[i] = middle_to_final[old_to_middle[i]]`。确认每个有权重索引在中间表中有定义；不要凭版本号排序对同一文件反复运行几个修复器。
- 共同顶点可作交叉验证：坐标在合理容差内、非零权重对应且候选唯一才计数；记录覆盖了哪些骨骼/部件及冲突。只匹配到头部不能宣布身体/翅膀映射都正确。镜像/重复顶点、不同坐标系或不同拓扑不允许自动取最近点映射。
- 只有局部骨骼语义或拓扑改变无法用置换解决时，才考虑针对明确部件重新导出/绑权；不要先替换整个模型或从另一MOD复制Blend。

`scripts/remap_blend.py`接受如下**格式示例**，数值必须换成实际查证的数据；它不会推断映射：

```json
{
  "schema": 1,
  "direction": "old-to-new",
  "source_version": "原包曾工作游戏版本",
  "target_version": "目标游戏完整版本或修订",
  "source_sha256": "原始Blend文件的64位SHA256",
  "layout": "le-f32x4-u32x4-stride32",
  "target_bone_count": 117,
  "old_to_new": {"4": 68, "5": 49},
  "evidence": ["记录骨架/帧dump或已核对修复表的具体位置和摘要"]
}
```

上面的两行来自历史温迪案例，仅示意字段；不覆盖所有有权重索引，不能直接用于真实文件。实际表可为完整数组或十进制键的对象，必须覆盖源文件出现的每个非零权重索引，并且目标索引均小于目标骨骼数。零权重索引不参与映射，可保留哨兵值。

执行前由文件摘要确认是原始数据。预览应列出顶点数、有权重槽数、将改变的槽数和输出摘要。确认后写**不存在的输出文件**，再比较权重/顶点顺序/长度完全不变。已修复文件再次输入应因源摘要不符被拒绝；不要绕过这个检查来“再试一次”。脚本检查语法与数据一致性，映射语义仍需上述证据。

如新版本stride、骨骼槽数或数据类型已经不同，停止使用这个32字节专用脚本，先读正确布局，再按新字段重打包。

## 5. 几何正确后修材质

在相同模型与相同DDS下，只调整必要的绑定，以区分数据问题与渲染接口问题。

- 核对当前draw是否真的使用NormalMap、Diffuse、LightMap，以及每一项落在哪个`ps-tN`。文件名称不等于Shader语义；读取资源与程序采样证据。
- 在已安装的ORFix版本中核对文档及实现：无NormalMap的部件可用`CommandList\global\ORFix\NNFix`；有NormalMap走它对应的ORFix入口。先确认库实际被include、支持目标游戏且调用发生在纹理绑定之后；不要不分部件统一加NNFix。
- 旧`MetalMap`、`ShadowRamp`的槽在新Shader可能已有别的用途。仅在目标draw/库实现支持时移除或改绑这些旧行，保留原图和声明便于对照。正常材质不需要重压缩或重画贴图。
- 遇到TexFx，读取该MOD真正调用的命令和模式。t69红通道不一定等于纹理alpha；t70与普通颜色分离。只实现用户要的兼容范围，不顺便加入新特效。

用户明确要求新配色、图案或透明效果时，可以修改对应纹理/材质/Shader，不受“修复时保持原图”的对照方式限制；区分所需设计变更与修复绑定错误，按 [定向修改](mod-editing.md) 保留无关区域和通道。

材质前后截图中几何/纹理字节未变而色彩恢复，是“绑定修复有效”的证据；不代表全光照、所有mip和透明层次已验收。

## 6. 验证与交付

在独立候选中运行结构检查及原/改后快照对比，变更文件应能解释。正常情况下保留原模型、IB和贴图，除非已经证实它们也需要转换。

按变化选最少的有效运行测试：hash命中/相关部件显示；涉及骨骼时静止与运动、受影响翼部动作；材质改动时清楚的同场景截图；涉及对象重建时传送/角色切换/原装停用。顶点扩容等创建时设置需要真正重建对象，F10仅配置重载不足以证明它生效。只有本机已验证热重载对该变化有效才省去重建。

如角色操作由用户完成，让用户做必要动作，助手检查具体那次日志/截图。记录短暂“未就绪”及其后续恢复，不把等待都当永久错误，也不隐去未解决失败。用户明确暂缓的细节可列为未验证而交付已完成范围，不能反复强推同一个检查。

报告原包、目标版本、依赖、改过的文件和未改的艺术数据，附清晰回退：只撤换本次候选或还原备份；不要重置全局MOD目录或游戏prefix。发布、覆盖、切换真实活动MOD由当前任务授权决定。

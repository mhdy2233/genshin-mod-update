# iOS 原生 MOD：披风、材质与 Metal 特效

用于 iOS MOD 修复、同版本外观/特效修改和 PC→iOS 资源适配。先沿 [定向修改](mod-editing.md) 确定目标，再使用本页的原生对象与程序链。已验证实例是 iOS 7.0.0 / build 1224、资源修订 47194594、R8 + LC1 + DATA1 的 [流浪者披风与暗红特效](ios-wanderer-cape-fx-case.md)。其它版本、角色和加载器需要新的目标证据。

本页提供资源修改流程；`scripts/convert_android.py` 仍只接受安卓预设。iOS 案例工具、已提取资源和 LLVM 环境依赖见案例末尾；复制技能即可阅读这些经验，执行转换还需相应输入。

## 固定平台与资源身份

核对实际 `.lunamod`、清单中的游戏版本/主程序 UUID、完整 IPA 基线，以及源块修订。PC 的 BUF/DDS/INI 表达几何、图案与效果意图；目标 Mesh/骨架、材质布局、Metal 程序和加载路由以 iOS 原生数据为准。Android 的引擎偏移、JNI/GLES/SPIR-V 与 PC 的 DXBC/ShaderRegex 不在 iOS 执行。

本例几个数字属于不同的字段，不能混用：

| 字段 | 本例值与含义 |
| --- | --- |
| 清单/SerializedFile 平台 | `9`，iOS 资源 |
| Shader 程序平台表 | `[14]`，Metal |
| 子程序 GPU 类型 | `23` vertex、`24` fragment；仍需 AIR 阶段元数据确认 |
| MOD 清单/资源布局 | `luna-ios-mod-v1` / `shared-native-v1` |

iOS Blb3 输入含明文 flag 4 和加密 flag 5；只支持安卓 flag 5 的旧读取器会报 `Invalid archive at 0`。先做目标样本原文往返，再编辑。资源链记录为：

`动作或角色形态 → prefab → renderer/材质槽 → Material → Texture/Shader → CAB/PathID → 原始 BLK 段`

保存源块相对路径、段 offset/bytes/SHA256、内部 CAB、FileID/PathID 与类型。内置资源、展示/远程/LOD 形态及 AssetBundle 预载表也是依赖；仅有一个 Body 或名字相似的资源不能代表全部入口。

## 披风串图：先定位图像与对象状态

截图若能对应到另一张已存在的图集，先比较目标与实际图像的像素摘要、UV、材质槽及 Texture2D 引用。静态指针正确只是第一层证据；克隆后仍同名的材质/贴图、游戏更新材质的时机和状态切换可能改变最终采样。

流浪者案例中 PC 披风属于独立 Hat 网格，应取 HatHead 图集；原 iOS Body/Hat 共享材质来源，新增 Hat 仍沿用 Body 名称，十个不同贴图对象又都沿用头发 Diffuse 名称。处理时：

- 对承担不同用途的新增对象按部件/贴图用途命名，并保留需要维持身份的原对象名；结合 PathID 和引用判断，不把所有同名原生对象判为错误。
- 核对影响当前 Shader 路径的属性与关键词是否一致。本例将 Body/Hat `_EnablePerformance=0` 对齐已经关闭的 `ENABLE_PERFORMANCE_ON`；不能把所有角色的性能模式统一关掉。
- 从最终重载的 CAB 逐一解析六种 Hat renderer → 独立材质 → Hat 图像，核对完整 mip 字节；原网格、骨骼、UV、图像与颜色空间保持时，无需重新导出/编码这些资产。

三项联合修正已获用户画面验收；具体由哪个运行时更新导致旧图像复用未单独取证。经验是同时检查引用、名称和状态，不能把联合通过写成某个缓存机制已被证明。

## 共享资源与私有作用范围

对共用 Mesh、图像、材质和程序分别去重。像素可共享而材质状态/对象名仍不同；不要按整个 `.resS` 摘要判断单张图像是否重复，也不要为了去重让 Body/Hat 再次互相覆盖。

特效按实际 prefab/renderer 选择目标。将所需 Shader 和材质复制为私有对象，目标 renderer 引用这些副本；保留原对象、官方 Shader 入口与非目标材质。相同原材质/Shader 在多个攻击中只复制一次，粒子曲线、变换、脚本、贴图和材质数值继续使用原数据。扭曲向量、不可见触发器和原装环模型表面由输出语义决定是否属于改色目标。

移动材质至公共 CAB 时，重算其纹理 FileID；`0` 指向本 CAB，外部 FileID 是从 1 开始的 externals 索引。保留目标 PathID，更新 renderer 指针、externals 和预载表，再从最终包验证整图。外部引用模板应选有效普通 CAB 项；本例为零 GUID、type 0。第一项可能是非零 GUID 的 `library/unity default resources`，不能盲目复制它。

R8 路由是原始段身份到修改段的映射：源 `source/offset/bytes/sha256` 标识原始 iOS 输入，`file` 指向输出资源，输出大小/摘要写在 `resources`。公共 CAB 可在原对象之外增加私有 PathID，保留内部原生引用身份；不要套用其它加载器“一律重命名所有 CAB”的策略。

## Metal/AIR 改色流程

只有当前材质的颜色参数能直接满足目标时，才只改参数。需要统一已合成颜色时，使用本例的原生 fragment 返回值修改方法，保留原 Shader 的纹理、动画与混合/深度路径。

1. **先证明程序解析正确。**原 Shader 元数据/程序表必须原样往返。空代码按 `dependent_blob_index`、同阶段和程序 hash 解析到真实代码；保留当前变体关键词和解析后程序的绑定尾表。`additional_blob` 的索引不属于 primary 表，不能直接套用。
2. **核对真实材质覆盖。**按每个目标材质的有效关键词集合检查每个相关颜色 pass 的 vertex/fragment 组合，要求精确匹配和非空检查。空 pass 名称也可能输出颜色；按 LightMode 与程序输出判定，不能只选名为 `MAIN` 的 pass。深度、阴影、运动、延迟中间数据和扭曲输出不能当最终颜色重染。
3. **确认 AIR 的阶段与目标。**读取 `!air.fragment`、输出元数据及 `air.render_target` 找到颜色目标 0。它可能是结构体返回值中的某一项，不能默认第一项或直接重写所有返回值。本例兼容实际出现的 `half4`/`float4`。
4. **只改要求的分量。**本例暗红目标为 `max(original RGB) * (0.650, 0.008, 0.028)`。从原返回向量提取 RGB，以原向量为基础仅插入分量 0/1/2，再放回原返回结构体。这样 alpha 和其它输出沿用原值；不改粒子曲线、原计算、discard、纹理、绑定和材质状态。目标要求透明度变化时另行验证 alpha/混合/深度，不能复用仅改 RGB 的验收。
5. **保持原 AIR 格式。**本例用 LLVM 14 读写原 typed-pointer AIR，保留 `air64-apple-ios11.0.0`、Metal 2.0 元数据、函数名、编译选项、输入输出和缓冲绑定。LLVM 19 会升级为 opaque pointer，不能仅凭新工具能解析就认为可替换。选工具以目标原样本及设备结果为依据，不把 14 写成所有版本的要求。
6. **重封并回读。**更新 AIR 包装长度/对齐、MTLB 总长、bitcode 段长度、`MDSZ` 与 `HASH`，再重新反序列化。私有 Shader 名称和程序缓存标记同步更新，避免继续命中旧程序。去重按程序内容进行；校验变体数与去重后实际改写数分别记录。

本例保留 primary 程序，13 个 Shader 的 57 套当前材质关键词获得 114 项精确阶段对照。额外压缩变体尚未完成解码，因此没有纳入。这个经过覆盖检查并获实机验收的取舍不意味着可以对其它 Shader 普遍删除 additional 变体；缺少目标匹配时应继续解码目标表或明确缩小范围。

class 200 是 ShaderVariantCollection，不因为位于 Shader CAB 就变成 ComputeShader 或附加字节码。遇到格式不符时按真实类型/阶段停在当前候选，保留失败输入及原因，再修改解析流程。

## 包、加载与验收

核对 ZIP 首项 `manifest.json`、成员集合、CRC、大小/SHA256、原生对象/流边界、每条路由与依赖；使用目标生产读取器检查。iOS 本例的内部流名为 `CAB-<32位非零十六进制GUID>.resS`，Texture2D 完整 `archive:/...` 路径同步修改。旧 `.luna.resS` 被本版游戏 GUID 解析拒绝；只改外层 `.blk` 文件名无效。写出器与自己的读取器都通过时，仍要对照官方命名或目标解析器。

R8 保存 MOD 只更新下次启动选择，资源路由在进程初始化安装；保存或恢复原装后完整退出游戏实例与 LiveContainer 再打开。切角色、小退或面板“已应用”不能替代该过程。日志出现旧缓存摘要时先确认实际选择/包身份，不能把旧包失败归到新包。

按改动分别记录文件/对象/程序检查和用户画面验收。用户明确反馈披风与攻击特效通过，就将对应结果记为通过；保留构建时的待测回执，新增当前验收记录。未逐项报告的动作、全局雾效、半分辨率/MSAA、全部图形档位、原装恢复和长时运行不自动继承通过。

包本身不因补写验收结论而重新生成。回退为恢复原装或选择保留旧包后完整重启。新制作或变更过的包单独验收，原案例的颜色公式、对象名、PathID、主程序 UUID 和工具路径只作为已固定证据。

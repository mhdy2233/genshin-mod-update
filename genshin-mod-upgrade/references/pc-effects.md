# PC 攻击与技能特效：修改和修复

适用于 GIMI/3DMigoto 下的攻击、重击、技能、拖尾、光效改色及相关加载错误。历史实例见 [黑红流浪者](wanderer-fx-case.md)。这里的方法需要当前客户端的绘制证据；案例的 hash、参数槽或热键都不是通用值。

## 1. 分清缺的是哪一层

核实当前启用目录、ShaderFixes、include、扩展库、全局 MOD 开关及效果触发条件。原包、用户正在用的目录和曾有效的环境可能不同；先比较文件清单/摘要，查独立特效目录或旧安装说明。

皮肤正确而攻击不变时，保持正确皮肤，沿效果链查。旧包没有单独 FX 文件，只能说明该包没有显式提供这种文件；不能否定用户旧版见过特效，也不能认定任意反光 Shader 就是攻击程序。历史公开特效包可解释机制，但必须记录其游戏/加载器版本，不能直接安装旧 Shader 或只替换文件名中的 hash。

## 2. 用动作和实际绑定定位

取得满足当前问题的最少证据，复用已有代码和完整帧。普攻、重击、E 起手、悬浮攻击等可能使用不同纹理组合或不同 Shader；同一 PS 也可绘制环境、其他角色和多个效果层。

按每个相关 draw 保存：动作/帧、draw 序号、PS/VS 标识、有效纹理槽/hash、程序实际读取的常量与输出。对照静止或非目标绘制，得到“程序 + 输入组合 + 目标状态”的条件。帧间差集和程序相似度只能缩小候选，不足以证明归属；仍绑定但未被程序使用的槽不能当有效输入。

### 采集选择与已知代价

先看实际 `d3dx.ini` 和所有启用 INI 的诊断设置/显式 dump。只缺 draw/绑定就用加载器支持的纯文字模式；缺程序代码时考虑单独导出代码；缺纹理内容才针对所需资源抓取。不要默认全场景导出 RT、纹理和缓冲。

本项目 **XXMI DLL 1.2.3** 已核定的行为如下，其他版本先查对应配置说明/源码：

- `analyse_options = log` 对应保留位 `0x80000000`，没有纹理/缓冲/RT 导出位；`none` 不是该版本的可用替代值。外部 CommandList 的显式 `dump` 需要另查。
- `FrameAnalysisContext` 在创建时由 hunting/debug 设置决定。原进程没有该上下文时，F10 不能补建，需要用户以合适设置重启；上下文已有则不无故要求重启。
- `export_shaders` 在程序创建路径导出原始代码。缺失的既有程序不能靠反复 F10 保证导出；检查代码创建机制和当前缓存再决定下一步。
- 本机 F8/F10 分别绑定单帧采集/重载，不推广到其他配置。完整帧要有结尾/Present 命令，不能把中途截断的 dump 当完整证据。
- 全量资源抓取曾造成长时间停顿；`share_dupes` 的文件去重不免除 GPU 读回。发生卡死/异常停顿后先保存日志并撤回相关诊断差异，改用更窄的采集，不重复同一高负载方案。硬链接的名义总长度不等于实际占盘。

临时设置保存前后差异及回退条件；只撤回本任务的变化，不覆盖其他新改动。按项目约定让用户操作游戏，助手准备配置、读取本次结果。

## 3. 选择实际修改点

| 证据 | 修改方式 |
| --- | --- |
| 原规则控制了目标，但被错误条件或保存状态挡住 | 修正/扩展已证实的条件，保留原有有效分支，不直接删除所有限制 |
| 当前程序读取专用颜色参数，且可限定到目标 | 修改该参数或现有配置，验证其颜色空间与其他使用者 |
| 颜色来自目标专用纹理 | 修改对应纹理/通道或创建独立替换；先确认它不是灰度遮罩或共用贴图 |
| 色彩来自当前 Shader 的计算，前述控制点不足 | 基于当前程序最小修改输出/相关运算，保留未涉指令、输入/输出接口和原控制流 |

修复必须解释原行为为何失效；新改色以用户目标为依据。没有旧效果源值时，可以实现并交付新的暗红候选，但应说明其色值是本次选择，不能宣称还原了旧版所有像素。

已确认某个输出确为最终颜色时，一种保持原亮暗分布的改色是：

```text
level = max(original_rgb.r, original_rgb.g, original_rgb.b)
modified_rgb = level * requested_colour
output_rgb = target_draw_enabled ? modified_rgb : original_rgb
output_alpha = original_alpha
```

这是颜色变换示例，不是所有特效的固定算法。历史深红系数为 `(0.65, 0.008, 0.028)`；新任务按用户目标选择。先查输出是否为 HDR、预乘 alpha、延迟缓冲或其他编码，避免给非颜色输出染色、擅自钳制亮度或改变原混合语义。若用户要改透明度/亮度/形状，则修改相应控制点并验证其额外影响，不能机械套“只改 RGB”。

### 限定作用范围

将角色/本套皮肤实际激活、全局开关及目标程序/纹理组合共同纳入条件。不要仅因流浪者在队伍里就给所有共用粒子染色。临时绘制参数按实际执行顺序恢复；每帧跟踪变量在相应帧末重置；关闭或切换后原效果能恢复。角色在 E 等状态下是否仍绘制激活部件，要以对应帧核实。

普攻已通过而重击/E 未变时，先查新 draw 的程序和输入。共用 PS 可用新增组合 OR 扩展原条件，不覆盖已通过的组合；确实有新程序才补新变体。不要因存在同类 PS 就一次全部全局改色。

## 4. ShaderRegex 要通过加载器这一层

采用 ShaderRegex 时，用当前程序的声明、足以区分变体的指令和输出片段限定匹配，保留其余代码。共享 PS 的目标绘制仍由上面的运行条件限制。匹配顺序先放廉价、精确的前缀，再比内部特征和尾部，避免每个无关程序都进入长通配搜索。

**XXMI 1.2.3 的三个已实证陷阱：**

1. 每组只接受 `.Pattern`，替换段为 `.Pattern.Replace`；`.Pattern0/.Pattern1` 会让整组被禁用。需要多个约束时，将它们组合进一个 pattern，用命名捕获保留中间原指令。不同程序仍用不同组。
2. INI 解析器把任意行首 `[` 当段头，用首个 `]` 截断。模式正文独立一行写 `([\s\S]*?)` 与写 `[\s\S]*?)` 的含义不同；后者会被当作段头。历史修复将已有捕获内的该行改成 `(?s:.*?))`，避免行首方括号；必须连同周围括号检查，不全局盲替换。
3. INI 会去掉每行首尾空白并拼接模式/替换文本。检查送到 PCRE2 的实际字符串、字面 `\n`、捕获回填及 `${...}`，不只在 Python 正则中验证源文件片段。

新增临时寄存器使用实际加载器的 `temps` 机制，核对原 `dcl_temps`、替换后寄存器范围和声明。访问运行参数时核对本机的资源机制、资源声明及可用参数槽；本案例的 `t120/x197` 不能当通用空槽。只改颜色时保留各分支原计算，将中间 RGB 存到新寄存器，原 alpha 写入与非目标路径需独立核验。

## 5. 共享标记和配置冲突

对照实际启用的 Core/Mods/include，检查新增 TextureOverride 的 **hash**、`filter_index`、namespace 和参数槽。数值标记空闲不代表纹理 hash 没有被库声明；仅盘点目标 MOD 看不到共享冲突。

若某纹理已经有语义一致且确实加载的共享标记，优先复用。历史 `cb888b02` 已由 Tracking 库赋予 `111.69`；候选重复声明 `705533` 触发冲突。删除重复段并在原三纹理判断中引用共享值即可保留效果，且必须记录该依赖。不要为消除警告就随意加 `match_priority` 或覆盖共享库；确需不同执行顺序时说明为何以及实际影响。

## 6. 用相应证据验收

- **文件/加载器语法**：按目标加载器解释段头、支持的子段、拼接及变量；`inspect_mod.py` 的零盘点警告不等于该项通过。
- **程序与条件**：用加载器对应的原生 PCRE2/标志检查匹配和替换，针对相关缓存程序确认目标命中及非目标排除；检查 alpha、未涉代码、寄存器/资源声明。再用捕获绑定验证选中的具体 draw。不要要求无关全盘扫描来代替有效负例。
- **运行加载**：读取正确进程/最近重载段，区分未知段、整组禁用、正则错误、组装失败和重复 hash；普通 `Patch did not apply` 可是非目标程序，`show_warnings=1` 是设置值。实际匹配的组数不等于所有目标 draw 都满足运行条件。
- **画面**：检查所改动作与必要的关闭恢复/其他绘制对照。用户确认“特效可见”不等于所有层、全部动作与其他角色已逐项通过；避免反复要求已通过且未改变的动作。

收尾时同步启用目录、包、说明及回执，保留失败版本和可读 diff，撤回已完成的临时取证设置。中断续接先核对实际文件和后续日志；文件可能已更新而包滞后，日志也可能已有无需重复的成功测试。
